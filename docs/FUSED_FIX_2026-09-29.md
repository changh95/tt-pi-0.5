## 2. The two bugs and the fix

Both bugs were present in the port and also in its torch oracle. Because the oracle had the same bugs, no PCC test
could catch them.

1. **No padding mask.** The server right-pads the prompt to 224 tokens. The VLM prefix and the action expert both
   attended those pad tokens.
2. **Expert RoPE.** openpi places the action tokens at positions `n_valid_prefix + [0, H)`. The port rotated them
   at `[0, H)`.

**Torch reference** (`reference/torch_pi0_model.py`): a new function, `prefix_attention_inputs(prefix_pad_masks, H)`,
builds openpi's inputs from the pad mask. These are the prefix key mask, the prefix positions `cumsum(valid) - 1`,
and the expert mask and positions `n_valid + [0, H)`. `forward_inference` passes them to `forward_vlm` and
`forward_expert`, which had always accepted them but never received them.

**Fused graph** (`e89eff8`):
- `common/fused_host.py` adds `prefix_valid_mask` and `attention_inputs`. Both are torch only, so the host tests
  can check them. `attention_inputs` builds these host tensors:
  - the VLM key mask `[B,1,P,P]`
  - the fused-attention key row `[B,1,32,P+S]`, which also hides the suffix's tile-padding rows
  - the ttnn-SDPA mask `[B,1,S,cache_len]`
  - the RoPE rows `n_valid + [0,S)`, with the scale and the rotate-half sign folded in the same way the fused
    kernel expects
- `PI0ModelTTNN` holds these tensors as **persistent trace inputs**: the masks in DRAM and the RoPE tables in L1.
  They are written with `copy_host_to_device_tensor` outside the capture, and only when the prefix validity has
  changed since the last call. `sample_actions_fused(..., lang_masks=None)`: when `lang_masks` is None, the mask
  is taken as `tokens != 0` (PaliGemma `<pad>` = 0). The prompt must be right-padded; anything else raises
  `ValueError`, because the prefix RoPE uses `0..P-1`, which equals openpi's `cumsum - 1` only for right padding.
- The fused expert attention kernel (`tt/kernels/fused_attn/{reader,compute}.cpp`, `tt/ttnn_fused_attn.py`)
  changed in three ways:
  - The additive mask now covers every key tile. Before, it covered only the last tile. The mask is applied in
    place, in the same way as the exp pass.
  - Each request in the batch reads its own RoPE tables and mask row. This means **batch > 1 with different
    prompt lengths is supported** on the default path.
  - The mask CB grows by NKt tiles, which is 50 KB per core at 224 tokens and H = 50.
- The `PI05_EXPERT_ATTN=ttnn` path now uses `sdpa_mask`, `cos` and `sin`. It supports only one prompt length per
  batch; otherwise it raises `ValueError` with an explicit message.
- **Configurable H and lang_len.** The expert suffix length now comes from `config.action_horizon`; before, it was
  hardcoded to 50. The cache length now covers the fused attention's 4-tile-row prefix reads. Before, 544 + 10 was
  refused. Each shape gets its own captured trace.
- `server/app.py` passes `lang_masks`. The batching workers rely on the `tokens != 0` default.

## 3. Proof

### (i) LIBERO shape vs the openpi GPU golden

The golden is `libero_eval/pi05/openloop_golden.pt`: 8 real observations with fixed noise. The run used
lerobot/pi05_libero, lang_len 32 right-padded, H = 10 and 10 steps. The metric is PCC over the 7 normalised action
dims.

| path | PCC7 mean | PCC7 min | file |
|---|---:|---:|---|
| old eager workaround (`libero_tt/tt_pi05_policy.py`, mode=openpi) | 0.9828 | 0.9037 | earlier run (target) |
| **fused traced, fixed (this branch)** | **0.99984** | **0.99971** | `fix2_libero.json` |
| torch reference fixed (fp32 CPU), lang_len 32 / 224 | 0.999995 / 0.999995 | 0.99999 / 0.99999 | `ref_vs_openpi.json` |
| torch reference NOT fixed, lang_len 32 / 224 | 0.966 / 0.440 | 0.875 / −0.549 | `ref_unfixed_control.json` |

In the fixed reference, changing the padding length from 32 to 224 changes the actions by at most 1.5e-7. The
padding is invisible, as it should be.

### (ii) Base served shape with padded prompts vs the fixed torch reference

The run used pi05_base, 224 tokens and H = 50. The prompts had a real prefix of N ids followed by `<pad>`.

| N real | 40 | 97 | 12 | 150 | 201 | 224 (unpadded) |
|---|---:|---:|---:|---:|---:|---:|
| PCC | 0.9984 | 0.9840 | 0.9381 | 0.9955 | 0.9802 | 0.9879 |

The mean is 0.980 (`fix2_base.json`). The 0.938 comes from the seed, not from the padding. The same seed with no
padding gives 0.961. Three other seeds with only 12 real tokens give 0.997, 0.996 and 0.991, which is the same as
their unpadded values of 0.996, 0.998 and 0.996 (`diag_base_seed.txt`). Random-input PCC for bf16 against fp32 has
always spread this widely; the p300x2 README reports 16 random observations with a minimum of 0.93. The gates in
`test_pcc_pi05_fused.py` are a minimum of 0.95 per observation and a mean of 0.98.

### (iii) The fix is live

These checks use the N = 40 prompt:
- Treating the pads as real tokens changes the output a lot: PCC −0.67 against the masked output, max|d| 1.66.
- Filling the pad slots with random ids under the same mask gives a **bit-identical** output, so the pads are
  exactly invisible.
- The default mask (`tokens != 0`) is bit-identical to the explicit mask.
- The host test `test_expert_attention_inputs_match_openpi_attention` emulates the kernel's math in fp64 against
  the reference attention with openpi's mask and positions, at batch 2 with two different prompt lengths. It
  matches to 1e-10. A positive control swapped each bug back in (RoPE rows at 0, or no mask) and the test caught
  both (max|d| 0.35 and 0.21).

### (iv) Ten-replay bit-identity

Ten replays were bit-identical at both shapes (`ten_replays_bit_identical: true`). Every trace was captured
(`traced: true`).

### (v) Traced latency

All figures are medians over 60 runs.

| shape | before (unfixed, same code) | after (fixed) | cost of the fix |
|---|---:|---:|---:|
| base 2×224², 224 tok, H 50: per call / replay | 83.0 / 81.6 ms | **84.2 / 82.8 ms** | +1.2 ms (VLM mask read in 18 SDPAs + NKt mask adds) |
| LIBERO 2×224², 32 tok, H 10: per call / replay | refused: `ValueError: fused expert attention built for 64 suffix rows, got xqkv rows 32` (`prefix_libero_unfixed.txt`) | **76.9 / 75.6 ms** | — |
| for reference: old p150 fused (a), base shape | 125.9 / 124.8 ms | — | — |

The pruned code produced the same PCC values, to all printed digits, as the pre-pruning run (`fix1_*` vs
`fix2_*`), and the same latency to within 0.2 ms.

  `embed_language_tokens`

## 6. Open problems

- **tt-metal pin.** The port was validated on the local gr00t tree 668c2907 (v0.79.0-dev20260914), not on the
  p300x2 pin 975015c2. The generic_op kernels depend on the compute API, which is why they failed on the June tree.
  The image build must use a tree that has been re-validated with these tests, or pin 668c2907.
- **Server not exercised on the device in this stage.** fastapi is not installed on the host, so only
  `py_compile` ran. The server's mask plumbing is one argument, but it should be checked with `smoke_test.py`
  when the server is served.
- **Untested after the fix:** the mesh / TP path (the fix is written mesh-aware with replicated persistent
  inputs, but there is no mesh here), `PI05_EXPERT_ATTN=ttnn`, `PI05_EXPERT_NORM_FOLD_ATTN`, and batch > 1. Batch
  > 1 is supported by the kernel's per-request operands but was not run on the device.
- **Masked cameras** (`img_masks` False) are not supported. A missing camera is still sent as a black image, as
  before. openpi would mask it, which would also shift the language positions.
- **Random-input PCC** at the base shape ranges from 0.94 to 0.998. That is inherent bf16 variance, but the
  LIBERO golden (0.9998) is the meaningful check.
